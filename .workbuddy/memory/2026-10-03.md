## 核心结论：ID 不能用中文（物理约束，非风格偏好）
用户要求"模组内所有故事/物品命名都用中文"，但准确落点是 **ID 用 ASCII 拼音、玩家可见文本用中文**，理由三条：
1. 原版 `ResourceLocation` 只允许 `[a-z0-9_.]` → **中文 ID 加载期直接崩**（不是警告，是崩）
2. 1.21.1 掉落表路径由注册名唯一推导（`BlockBehaviour` 用 `withPrefix("blocks/")`）→ ID 与掉落表路径是**同一条约束**
3. Java 标识符可含 Unicode 但不可含 `-`；CSV 表头是列契约（改列名=破档）

**中文化审计结果（已达成，无需再动）**：lang 109 条全部含汉字、零空串、zh_cn/en_us key 双向完全对齐；对话正文 41 条全中文；代码内玩家可见文案 20 处全中文。

## 关键设计决策：把文档规范落成机器门禁
docs/11 规范若只写文档会漏，所以新增第 12 项门禁 **V-NAME**（`NameConventions.java`）：
- 查**源表与产物两侧**的 ID 形状（只查一侧会漏：只查产物要等 DataGen 后才发现，只查源表则产物被手改漏）
- 拦中文 ID 并在报错里说清"会崩"而不只是"不合规"
- lang key 三段式；**zh_cn 值必含汉字**，en_us 按 ADR-009 允许占位
- 台账表（`known-placeholders`/`id_migration`）走 `isLedgerTable` 豁免形状，只查非 ASCII 字母
- **20 条用例每条规则都有红脸**——一个永远返回空的门禁比没门禁更危险，因为它看起来在工作

## 工具使用教训（本机 Windows + Git Bash）
- **shell 里 grep/sed 看中文会显示成乱码**（如 `月来æ¸`）——那是 Git Bash 按 GBK 解码 UTF-8 的**显示假象**，文件本身干净。**判定编码问题必须用 Python 读字节**（`read_bytes()` + `decode('utf-8')` + 往返还原检测），不要信终端显示
- `gradle -q` 会吞掉 `datagen:`/`validator:` 统计行
- `grep ... | head -N` 会被满屏 `UP-TO-DATE` 占满看不到 BUILD 行 → 用 `tail`
- **用 Python 写文件会绕过 `core.autocrlf` 归一化**，导致工作区 CRLF 与 `.gitattributes` 声明的 LF 不一致（git add 时才归一化，所以 `git status` 可能显示 modified 又 add 后无差异）
- 判行尾真相要**从 git 对象读原始字节**（`git show HEAD:file` 经管道会被转换），别看工作区
- `core.autocrlf=true`（本机已设）+ `.gitattributes` 的 `eol=lf` → 仓库存 LF、Windows 检出 CRLF，**这是正常行为不是缺陷**；`.bat` 按规则就是 CRLF
- spotless 对 Javadoc 换行宽度敏感（本轮 `spotlessCheck` 红过一次）→ `spotlessApply` 后必重跑门禁
