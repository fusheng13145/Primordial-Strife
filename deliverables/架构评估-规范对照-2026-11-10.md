## 4. 为什么不做"接入/业务/领域/数据访问"全量包改名（兼容性影响点全列出）

全量改名若执行，涉及：178 个 Java 文件的 package/import、`ModuleDependencyRules`（CI 守卫重写）、
docs/03（真相源结构描述）、AGENTS.md 包根规范行、全部 ADR 引用、5 个注册器（DeferredRegister 的
注册 ID 不变但类路径变）——**改动面 ~全部源码，功能价值 ≈ 0**，具体冲突：

1. **运行时形态不适配**：NeoForge 的 `@Mod` 入口 + DeferredRegister + 事件监听不是 Servlet 请求模型。
   "接入层"（clientfx + 命令）与"业务层"（handler）在 MC 里是同一个类——强行拆分会让一个
   `attemptBreakthrough` 命令要穿过 access→business→domain 三层四五个类才能改一次数值，违背手册自己的
   "可维护性"初衷。
2. **"数据访问层"不存在对应物**：运行时数据 = DataGen 产物（classpath JSON，构建期校验）+ 原版注册表 +
   附件 codec。没有 dao/mapper 可抽——硬造一层"XxxRepository"包着 `getResourceManager().open()` 是伪分层。
3. **门禁重写风险**：`ModuleDependencyRules.allowedTargets` 按包名白名单检查；改名后守卫必须同批重写，
   否则失去比手册更强的依赖防回归机制。
4. **兼容性影响点**（若本人仍裁决执行）：远程 75+ 提交历史中所有涉及 `com.strife.realm.*` 等路径的
   引用描述失效；`docs/03/07/10` 三分册结构与示例需同步重写；外部（若有）fork 的 diff 全部冲突。
   建议：若确需对齐手册术语，采用**映射表**（本文档 §1 括号内已给出：core=公共层、clientfx=接入层、
   各特性包=领域+业务）而不改物理结构。
