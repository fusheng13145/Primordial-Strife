## 4. 关键设计决策

### 4.1 矿石：为什么是"五份产物"而不是一份

矿石 placement 在原版 1.21 世界生成里是一条**链**：configured feature（形状与替换规则）→ placed feature（次数/大小/高度/噪声）→ biome modifier（挂到哪些群系的哪一步）→ 掉落表 → strife 侧契约镜像。四个环节任一缺失，矿石都不生成，且原版不报错（它只是找不到那条链）。

故 DataGen 必须整条链一起写，让"表里有的矿一定在世界里出现、且破坏一定掉东西"成为**构建期事实**，而不是运行时祈祷。

### 4.2 掉落表路径由注册名强制推导（1.21.1 源码实证）

M4 批最重要的发现，直接推翻了一个设计：`tables/ores.csv` 的 `drop_table` 原填 `loot_ore_lingyu` 这类自由命名（理由是"掉落表应该是内容 ID"），查源码后结论相反。

| 事实 | 证据 |
|---|---|
| 1.21.1 **没有** `LootableBlock` 接口 | 全 jar 搜 `lootable` 零命中 |
| `BlockBehaviour.Properties` **无公开** lootTable setter | 只有 `noLootTable()` / `dropsLike(Block)` / `lootFrom(Supplier)` |
| `Block.getLootTable()` 是 `final`，不可覆写 | `BlockBehaviour.java:370` |
| 路径由注册名推导 | `BlockBehaviour.java:120-122`：`BuiltInRegistries.BLOCK.getKey(block).withPrefix("blocks/")` |

写别的名字，原版找不到表就**静默不掉落**——矿挖了掉空气，且不报错。**处置**：`drop_table` 收紧为 `blocks/<方块ID>`，DataGen 与 `OreTables` 双重校验（前者构建期报"表名:行号"，后者运行期防产物被手改）——把由代码决定的路径**显式写进表里让人看见**，不靠约定。

### 4.3 解析器不碰注册表（分层纪律）

1.21.1 的 `BuiltInRegistries` **没有** `BIOME` 字段——群系是动态注册表，只能经 `server.registryAccess().registryOrThrow(Registries.BIOME)` 访问，而那需要已启动的服务端。若让 `OreTables` 依赖它：① 用例必须起服才能跑（与本仓"真实产物当夹具"的写法冲突）；② 加载期与运行期的失败时机混在一起。

**分工**：`OreTables` 只保证群系 ID **形状**合法（`ns:path`）；"ID 是否真实存在"由 `OreCommand` 在有注册表的运行时核对并逐条点名。

### 4.4 密度倍率的折算语义

`effectiveVeins = max(1, ceil(veins_per_chunk × density_ratio))`。

- **向上取整**：`0.85 × 8 = 6.8 → 7`，不四舍五入也不截断——避免系统性低估密度。
- **保底 1**：`0.15 × 2 = 0.3 → 1`。表作者写 0.15 的意图是"**稀**"不是"没有"，取整成 0 会让该矿彻底消失且不报错。
- **在生成期落成整数**：放矿是原版行为，运行时没有"读表再乘"的钩子，倍率必须在此处折算。

### 4.5 高度换算

原版 `height_range` 是"以地表为 0 的相对高度"（允许负值），`y_min/y_max` 是绝对高度，换算为 `height = yMax − (−64)`、`y = yMin − (−64)`。`−64` 是 1.21.1 的世界基线，属**平台常量**非受管数值（改动它意味着改 MC 版本），不进 NUMBERS。

### 4.6 方块属性不进 NUMBERS

硬度/抗爆性/材质色/声音是**材质属性**不是受管数值（与 `SpellProjectile.MAX_ALIVE=64` 同类）：不进 NUMBERS、不参与平衡流程，评审时按"像不像矿石"判断。显式说明，避免被误当成 06 §5 的字面量违规。

**技术常量清单**（全仓仅此几处，均已核实）：`MAX_ALIVE=64`（同屏弹道上限）、`MAX_CACHED_REGIONS=4096`（缓存容量）、`BLOCKS_PER_CHUNK=16`（MC 固有）、噪声归一化 `(noise+1)*0.5`。**修炼与战斗受管数值确实零字面量**（伤害/速度/重力/射程/冷却全部从产物读）。

### 4.7 为什么不从 Java 侧注册 BiomeModifier

原方案 `NeoForgeBiomeModifiers.add_feature(...)`：核实发现**该类型在 21.1.251 的 jar 中不存在**（记忆中的 API 已迁移）。改走数据驱动（DataGen 产出 `worldgen/biome_modifier/*.json`）：既核实了 API，又更符合 ADR-016"原语与剧本分离"，且新增矿石只动表 + 一个 `register` 常量。

### 4.8 灵气浓度场为什么必须挂在区块生成期（G-8 实测的连带发现）

docs/03 §6 红线写「新区块灵气场生成 ≤2ms/chunk（命中缓存 ≈0）」，手段一栏写「**区块生成期**计算 + 区域粗粒度缓存」；实测前的实现与之不符——全仓没有区块事件挂钩，灵气浓度场只在 `StrifeWorld.environmentCoefficient`（玩家查询时）惰性求值。后果不是"慢"，而是**成本出现在错误的位置**：玩家走向从未加载过的区域时，粗粒度采样落在**查询线程**上，产生冷启动尖峰——红线要避免的正是这个。

**处置**：新增 `AmbientQiWarmup` 挂 `ChunkEvent.Load`，只处理 `isNewChunk()` 为真的事件（重载既有区块不需预热）。选 `Load` 而非 `ChunkDataEvent`：后者触发于区块序列化阶段、那时区块尚未可查询，`Load` 才是"区块已可被游戏逻辑访问"的时点。表不可用时安静返回——**世界生成期绝不能因附加逻辑抛异常**。

**实测数字**（`AmbientQiBenchmarkTest`，生产同款 `ImprovedNoise`，固定种子 20261003，n=256）；热比冷快 3.2 倍，证明缓存真实生效而非摆设：

| 路径 | 平均 | p50 | 最大 | 红线 2ms |
|---|---|---|---|---|
| 冷（跨区域，缓存未命中） | **0.0090ms** | 0.0041ms | 0.19ms | 低 222 倍 |
| 热（同区域内，命中缓存） | **0.0028ms** | 0.0009ms | 0.11ms | 趋近 0 ✅ |
| 方块查询（玩家实际路径） | **0.0011ms** | 0.0006ms | 0.046ms | 低 1800 倍 |

**为何用真实噪声**：`AmbientQiFieldTest` 那 7 例用假噪声钉行为（上下限/区域粒度/缓存命中/非零），换任何噪声实现都成立；而**假噪声比 `ImprovedNoise` 快一到两个数量级，拿它报毫秒数是自欺**。所以这是全仓唯一必须用真实 MC 噪声的测试。

**断言为何宽松**（红线 10 倍 = 20ms）：CI 机与本机 CPU 差异可达数倍，绑死 2ms 会让门禁随机红；宽松上限只兜**数量级退化**（例如误把缓存改成每次重采样），真实读数靠 `ambient-qi-bench` 打印行 + 本节入档。

**区域粒度的陷阱**：区域是 `floorDiv(chunk, 16)`，构造"同一区域"的重复采样只能靠 `% 16`。用 `chunk=i*16` 会落在第 i 个区域（256 块 = 256 个区域，热路径根本没走到）；改用 `i/16` 铺开，则 `i<256` 时只有 0..15、`baseX` 固定仍是同一区域，算出的 16 次采样实际只有 1 次。

### 4.9 妖兽属性在 @@combat、刷怪判定自实现的原因

- **属性放 `@@combat`**：`ModuleDependencyRules` 禁 `combat→world` 横向依赖。`beast_loot_rolls` 早在 `@@world`（掉落 roll 属世界掉落语义），但妖兽战斗属性是战斗语义，必须由 combat 自己的产物承载——`CombatTables` 只读 `strife_combat/rules.json`，与 `WorldTables` 同理念不同侧。代价是"rolls 在 world 域、属性在 combat 域"分居两侧，属门禁约束下的有意取舍。
- **刷怪判定自实现**：原版 `Monster.checkMonsterSpawnRules` 形参要 `ServerLevelAccessor`，该类型在 NeoForge 21.1 userdev 里不可作为可引用类型（gradle 缓存无此类文件，编译实证）；`SpawnPlacements.SpawnPredicate` 回调只给 `LevelReader`。与其依赖不可引用类型，不如在 `LevelReader` 上自实现等价核心（实心地面 + 光照 ≤8 + 非液体 + STRUCTURE 除外），零私有类型依赖。

### 6.3 单 PR 行数超限（D-P0-4 已裁决：同一交付链例外）

`AGENTS.md` 硬规则写"单 PR 逻辑代码 ≤400 行（生成物/文本除外）"。M4 矿石批实测（文件与逐行明细见 §5.1）：主源码四件合计 **1121 行**，去注释与空行后 **818 行逻辑代码**；测试另计 `OreGeneratorTest` 320 + `OreTablesTest` 312（规则未明确豁免测试）。

**为什么超**：五份产物共享同一份表结构，拆成多个 PR 会产生**中间态**——只提交生成器不提交解析器、或只提交解析器不提交产物，都会让 CI 绿但运行时断链（本仓最贵的一类缺陷，§4.1）。

**既有实践**：`0a28435`（迭代 8）+1716 行、`4e6ba0e`（M4 批）+2546 行，均超限——"一次迭代一次提交"是本仓既成做法，规则与实践长期不一致。

**已做的处置**：① 提交拆成 `4e6ba0e` 交付 + `d08e383` 修复，功能与修复分开便于回滚；② 大段 Javadoc（占主源码约 300 行）承载 1.21.1 源码实证结论，防止后人重犯"以为 `drop_table` 可自由命名"，不算注水；③ **未擅自改门禁、未删测试、未拆出无意义的碎片提交**。

**本人裁决（2026-10-25，D-P0-4）：方案一**——单 PR 逻辑代码仍以 400 行为基线，**同一交付链的多文件例外**，但需在 PR 描述列出文件清单与耦合理由。规则已写回 `AGENTS.md` 与 06 §5，不再存在"事实运行但不声称合规"的状态。
